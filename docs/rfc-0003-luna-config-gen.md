## Overview

This RFC defines Luna's configuration generation system.

The goal is to dramatically reduce configuration sprawl while maintaining compatibility with ecosystem-native tooling.

This RFC introduces:

- `luna sync`
- Generated configuration
- Template-based scaffolding
- Drift detection
- File ownership rules
- Generation boundaries
- Workspace synchronization

This RFC intentionally avoids generating framework-specific application configuration during the initial implementation.

## Problem Statement

Modern monorepos accumulate large amounts of repetitive configuration.

A typical TypeScript package may require:

```text
package.json
tsconfig.json
tsconfig.build.json
eslint.config.js
vitest.config.ts
moon.yml
```

Many of these files repeat the same metadata:

```text
Project Name
Project Type
Dependencies
Entry Points
Build Outputs
Tags
```

This creates:

- Duplication
- Drift
- Maintenance burden
- Difficult onboarding
- Inconsistent project setup

## Goals

### Goal 1

Reduce repetitive configuration.

### Goal 2

Centralize workspace metadata.

### Goal 3

Generate only low-risk configuration.

### Goal 4

Preserve ecosystem compatibility.

Generated files must still work with:

- Bun
- TypeScript
- Moon
- VSCode
- IDEs
- CI

### Goal 5

Avoid framework lock-in.

Luna should not require:

- SolidStart
- FastAPI
- Hugo

to change how they operate.

## Non-Goals

### Not A Build System

Luna does not replace:

```text
Moon
Vite
Cargo
Go
```

### Not A Package Manager

Luna does not replace:

```text
Bun
uv
Cargo
Go Modules
```

### Not A Framework Generator

Luna does not generate:

```text
solid.config.ts
vite.config.ts
hugo.toml
next.config.ts
```

during Phase 1.

## Design Philosophy

Configuration should exist in one of three categories.

### Category 1

Human Authored

Examples:

```text
luna.yml
.prototools
```

Developers own these files.

### Category 2

Generated

Examples:

```text
package.json
tsconfig.json
workspace references
```

Luna owns these files.

### Category 3

Application Owned

Examples:

```text
solid.config.ts
hugo.toml
go.mod
pyproject.toml
```

Applications own these files.

## luna sync

The centerpiece of configuration generation.

### Purpose

Synchronize the workspace.

Example:

```sh
luna sync
```

Responsibilities:

- Generate configs
- Update configs
- Detect drift
- Validate workspace

### High-Level Flow

```text
Load luna.yml
        ↓
Discover Projects
        ↓
Build Workspace Model
        ↓
Generate Configurations
        ↓
Detect Drift
        ↓
Write Changes
        ↓
Report Results
```

All generated files originate from:

```text

```

### Example

```yaml

  app:
    language: typescript
    framework: solid-start
    layer: application

  ui:
    language: typescript
    type: library
```

## File Ownership

Every generated file must have a clear owner.

### Luna-Owned

Examples:

```text
package.json
tsconfig.json
workspace references
```

Header:

```text
AUTO-GENERATED
DO NOT EDIT
Generated by Luna
```

### Developer-Owned

Examples:

```text
vite.config.ts
solid.config.ts
```

No generation.

## TypeScript Generation

TypeScript offers the largest immediate win.

## Generated package.json

Source:

```yaml
projects:
  ui:
    language: typescript
    type: library
```

Generated:

```json
{
  "name": "@luna/ui",
  "private": true,
  "type": "module"
}
```

### Why Generate?

Most package manifests repeat:

```text
name
private
type
exports
workspace metadata
```

These are predictable.

### Not Generated

Dependencies remain ecosystem-owned.

Example:

```json
{
  "dependencies": {
    "react": "^19.0.0"
  }
}
```

Phase 1 should preserve dependencies.

## Generated tsconfig.json

Generated from templates.

### Library Example

```json
{

}
```

### Application Example

```json
{
  "extends": "../../configs/typescript/application.json"
}
```

## Why Not Generate Framework Config?

Framework configuration changes frequently.

Examples:

```text
Vite Plugins
SolidStart Adapters
Deployment Settings
Experimental Features
```

Generated ownership becomes problematic.

## Drift Detection

Luna must detect:

```text
Expected
vs
Actual
```

### Example

Expected:

```json
{
  "name": "@luna/ui"
}
```

Actual:

```json
{
  "name": "ui"
}
```

### Output

```text
Project ui

package.json drift detected

Expected:
  @luna/ui

Found:
  ui

Run:
  luna sync
```

## Drift Modes

### Informational

```sh
luna doctor
```

Reports drift.

### Automatic

```sh
luna sync
```

Repairs drift.

## File Metadata

Generated files include metadata.

Example:

```json
{
  "$generatedBy": "luna",
  "$version": "2"
}
```

or comment headers where supported.

## Dry Run Mode

Support:

```sh
luna sync --dry-run
```

Output:

```text
Would update:
  packages/ui/package.json

Would create:
  packages/ui/tsconfig.json
```

## Sync Modes

### Standard

```sh
luna sync
```

### Validate

```sh
luna sync --check
```

No modifications.

### Force

```sh
luna sync --force
```

Regenerate everything.

## Acceptance Criteria

Configuration generation is complete when:

- package.json generation exists
- tsconfig generation exists
- drift detection exists
- luna sync exists
- generated files are reproducible
- generated files are clearly marked
- framework configs remain developer-owned

## Architectural Decision

### Decision

Luna generates common boilerplate configuration while preserving framework-specific ownership.

### Rationale

This provides the greatest reduction in configuration sprawl with the lowest risk of developer frustration.

### Consequences

#### Positive

- Reduced duplication
- Faster onboarding
- Consistent project setup
- Easier workspace maintenance

#### Tradeoffs

- Additional generation layer
- Sync step required
- Generated files must remain predictable
- Template identity must be maintained
