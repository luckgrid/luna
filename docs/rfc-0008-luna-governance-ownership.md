## Overview

This RFC defines governance, ownership, compatibility, migration, and operational policies for Luna.

As Luna begins generating configuration and scaffolding projects, the following questions become critical:

- Who owns generated files?
- What files may developers modify?
- How are generator changes applied?
- How are template changes applied?
- How are breaking changes introduced during pre-alpha development?
- How are compatibility expectations communicated?
- How are migrations executed?

This RFC establishes those rules.

## Problem Statement

Without clear ownership rules, generated systems eventually create confusion.

Developers begin asking:

```text
Can I edit package.json?

Can I modify tsconfig.json?

Can I change generated metadata?

Can I delete generated files?

What happens after luna sync?
```

Without clear answers:

- Workspaces drift
- Tooling becomes inconsistent
- Changes become risky
- Contributors lose trust

Governance exists to prevent these problems.

## Governance Goals

### Goal 1

Establish clear ownership boundaries.

### Goal 2

Make workspace changes predictable.

### Goal 3

Prevent configuration drift.

### Goal 4

Maintain developer trust.

### Goal 5

Preserve long-term maintainability.

## Ownership Model

Luna defines three ownership categories.

## Category 1

Human Owned

### Definition

Files directly edited by developers.

### Examples

```text
luna.yml
.prototools

solid.config.ts
vite.config.ts

hugo.toml
go.mod
Cargo.toml
pyproject.toml
```

### Rules

Developers own these files.

Luna never modifies them.

## Category 2

Luna Owned

### Definition

Files generated by Luna.

### Examples

```text
package.json
tsconfig.json
workspace references
generated metadata
```

### Rules

Luna may overwrite these files.

Developers should not edit them directly.

### Required Header

Generated files must contain:

```text
AUTO-GENERATED
DO NOT EDIT
Generated by Luna
```

where supported.

## Category 3

Shared Ownership

### Definition

Files partially generated by Luna and partially extended by developers.

### Initial Policy

Not supported in the current refactor.

### Rationale

Shared ownership creates ambiguity.

Avoid until absolutely necessary.

## Generated File Policy

Generated files are disposable.

### Principle

A generated file should be reproducible from:

```text
luna.yml
```

plus workspace state.

### Rule

Deleting generated files should never result in data loss.

## Editing Generated Files

### Current Policy

Not allowed.

### Example

Incorrect:

```json
{
  "name": "@custom/ui"
}
```

inside a generated file.

### Correct

Modify:

```yaml
projects:
  ui:
```

inside:

```text
luna.yml
```

then run:

```sh
luna sync
```

## Drift Policy

Drift occurs when generated output differs from expected output.

### Example

Expected:

```json
{
  "name": "@luna/ui"
}
```

Found:

```json
{
  "name": "@custom/ui"
}
```

## Detection

```sh
luna doctor
```

## Repair

```sh
luna sync
```

## Change Management

Luna is still in early pre-alpha development, so the refactor is not managed as a release track.

Changes should be:

- Explicit
- Reviewable
- Reversible through source control
- Validated by `luna sync --check` or equivalent validation

## Generator Change Tracking

Generators should expose enough metadata to explain what produced a file without requiring release-managed migrations.

### Example

```text
Generated by Luna
Source: luna.yml
Generator: typescript-package
```

## Why Track Generators?

Generator metadata helps Luna answer:

```text
Who Owns This File?
Which Generator Produced It?
Can It Be Recreated?
```

## Template Identity

Templates should use stable identifiers instead of a release-managed change strategy.

### Example

```yaml
template: solid-app
language: typescript
kind: application
```

## Benefits

Stable template identity allows Luna to:

- Trace project origins
- Reproduce generated structure
- Explain scaffolding decisions
- Avoid premature template migration systems

## Compatibility Expectations

Compatibility is best-effort while Luna remains in early pre-alpha development.

The current policy is:

- Preserve existing application behavior where practical
- Keep generated files reproducible
- Make breaking changes explicit in the roadmap
- Prefer incremental migration steps

## Migration Strategy

Migrations should be simple, documented implementation steps rather than release-managed change flows.

Responsibilities:

- Detect drift
- Preview changes
- Apply changes intentionally
- Validate the workspace

## Migration Modes

### Dry Run

```sh
luna sync --check
```

Reports required changes without writing files.

### Interactive

```sh
luna sync --interactive
```

Reviews changes before applying them.

### Automatic

```sh
luna sync
```

Applies safe generated-file changes.

## Migration Flow

```text
Read Workspace Metadata
Detect Drift
Create Plan
Preview Changes
Apply Changes
Validate Workspace
```

## Deprecation Policy

Features should not be removed immediately when existing projects rely on them.

## Lifecycle

```text
Active
 ↓

Deprecated
 ↓

Removal Candidate
 ↓

Removed
```

## Deprecation Warning

Example:

```text
Warning:
Root package.json generation is deprecated.

A future refactor step will remove it after the replacement path is available.
```

## Override Policy

Overrides should be rare.

## Initial Policy

No overrides.

### Rationale

Overrides make generated systems harder to reason about.

## Future Override Model

A future RFC may define explicit extension points for workspace-specific policy.

## Workspace Trust

Developers must trust that Luna will not destroy work.

## Principles

- Never overwrite human-owned files
- Always mark generated files
- Provide dry-run modes
- Validate before applying changes
- Prefer explicit failures over silent rewrites

## Requirements

Generated-file writes must be:

- Deterministic
- Reproducible
- Auditable
- Recoverable through source control

## Documentation Requirements

Every generator must document:

```text
Inputs
Outputs
Version
Ownership
```

## Workspace Recovery

A workspace should always be recoverable.

### Example

Delete:

```text
Generated Files
```

Run:

```sh
luna sync
```

Workspace restored.

## Security Considerations

Generators must never:

```text
Execute Arbitrary Code
Modify Human-Owned Files
Transmit Workspace Data
```

without explicit user action.

## Acceptance Criteria

Governance is complete when:

- Ownership boundaries are defined
- Generated file policy exists
- Drift policy exists
- Change-management policy exists
- Migration strategy exists
- Deprecation policy exists
- Compatibility expectations are documented
- Workspace recovery is documented

## Architectural Decision

### Decision

Adopt a strict ownership model with deterministic generation, explicit migrations, and predictable workspace changes.

### Rationale

Long-term workspace health depends more on governance than implementation details.

Without governance:

- Trust erodes
- Drift increases
- Changes become dangerous

Governance creates the foundation required for Luna to scale over many years.

### Consequences

#### Positive

- Predictable workspace changes
- Clear ownership
- Easier maintenance
- Strong developer trust

#### Tradeoffs

- Reduced flexibility
- More upfront planning
- Migration infrastructure required
