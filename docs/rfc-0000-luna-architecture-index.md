## Purpose

This document serves as the entry point into the Luna architecture documentation set.

It provides:

- Project vision
- Architectural principles
- RFC navigation
- Ownership boundaries
- Implementation order
- Architectural Decision Records (ADRs)

This document should be read before any other RFC.

## What Is Luna?

Luna is a polyglot workspace runtime built on top of:

- Proto
- Moon
- Native ecosystem tooling

Luna does not attempt to replace existing tools.

Instead, Luna provides:

```text
Workspace Definition
Workspace Discovery
Configuration Generation
Developer Experience
Workspace Orchestration
```

while delegating execution and package management to existing tooling.

## Core Philosophy

Luna is not:

```text
A Package Manager
A Build System
A Task Runner
A Dependency Resolver
```

Luna is:

```text
A Workspace Runtime
```

## Source of Truth Hierarchy

### Tier 1 — Human Authored

Files directly owned by developers.

```text
luna.yml
.prototools
```

These files represent the authoritative workspace definition.

### Tier 2 — Generated

Generated by:

```sh
luna sync
```

Examples:

```text
package.json
tsconfig.json
workspace references
generated moon metadata
```

Generated files should be reproducible.

### Tier 3 — Application Owned

Examples:

```text
solid.config.ts
vite.config.ts
hugo.toml
pyproject.toml
go.mod
Cargo.toml
```

These files remain framework and application specific.

Luna does not modify them.

## Architectural Decision Records

This section captures the foundational decisions that shape Luna.

## ADR-0001

### Luna Is Not A Package Manager

#### Decision

Luna delegates package operations to ecosystem-native tooling.

#### Rationale

Existing package managers already solve:

```text
Dependency Resolution
Lockfile Management
Package Installation
Publishing
```

#### Consequence

Luna remains lightweight and focused.

## ADR-0002

### Moon Remains Authoritative For Execution

#### Decision

Moon remains the execution engine.

#### Rationale

Moon already provides:

```text
Caching
Task Pipelines
Dependency Graphs
Affected Detection
```

#### Consequence

Luna focuses on workspace concerns.

## ADR-0003

### Proto Remains Authoritative For Toolchains

#### Decision

Proto remains the runtime manager.

#### Rationale

Proto already provides:

```text
Version Pinning
Runtime Installation
Runtime Discovery
```

#### Consequence

Luna avoids toolchain complexity.

## ADR-0004

### Generated Configuration Over Manual Ownership

#### Decision

Common boilerplate configuration should be generated.

#### Examples

```text
package.json
tsconfig.json
workspace references
```

#### Rationale

Reduces:

```text
Duplication
Drift
Maintenance
```

#### Consequence

Requires sync and governance systems.

## ADR-0005

### Rust As The Runtime Language

#### Decision

Luna is implemented in Rust.

#### Rationale

Rust provides:

```text
Performance
Portability
Strong Tooling
Memory Safety
Static Binaries
```

#### Consequence

Cargo becomes part of Luna development.

## Success Criteria

The Luna refactor is successful when:

- Workspace metadata is centralized
- Configuration sprawl is reduced
- Moon remains authoritative for execution
- Proto remains authoritative for toolchains
- New ecosystems can be added without redesign
- The repository no longer feels TypeScript-centric
- Developers primarily interact through the Luna CLI

## Future RFC Candidates

The following RFCs are intentionally out of scope for the current refactor but represent potential future evolution paths for the platform.

### RFC-0009: Plugin System

Enable third-party and organization-specific extensions that can add custom adapters, generators, validators, commands, and workspace integrations without modifying Luna core.

### RFC-0010: Workspace Analytics

Provide visibility into workspace health, growth, dependency usage, build performance, ownership coverage, and other operational metrics.

### RFC-0011: Daemon Architecture

Introduce a long-running background process to improve performance through cached discovery, file watching, incremental updates, and workspace state management.

### RFC-0012: Remote Template Registry

Allow templates and project blueprints to be distributed through local, private, or public registries without tying the current refactor to a release lifecycle.

### RFC-0013: Multi-Repository Federation

Enable multiple repositories to be managed as a logical workspace with shared standards, metadata, tooling, and visibility across organizational boundaries.

### RFC-0014: Distributed Caching

Coordinate remote cache providers and shared build artifacts across developers, CI systems, and environments to improve performance and reduce redundant work.

### RFC-0015: Workspace Policies

Provide automated governance and architectural enforcement for dependency rules, ownership requirements, naming conventions, layering constraints, and security standards.

### RFC-0016: Workspace Service Catalog

Create a centralized inventory of applications, services, packages, infrastructure components, environments, and ownership metadata within the workspace.

### RFC-0017: Workspace Documentation System

Generate architecture diagrams, project catalogs, dependency maps, ownership reports, and other documentation directly from workspace metadata.

### RFC-0018: Workspace AI Integration

Provide structured workspace context, project graph access, and policy-aware automation interfaces for AI-assisted development workflows.

These RFCs are intentionally out of scope for the current refactor.
