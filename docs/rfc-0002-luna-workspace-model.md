## Overview

This RFC defines the workspace model used by Luna.

The workspace model establishes:

- The source of truth hierarchy
- Workspace metadata ownership
- Project registration
- Project discovery
- Moon integration
- Proto integration
- Workspace schema
- Future workspace expansion

The goal is to create a consistent metadata layer that sits above:

- TypeScript
- Python
- Go
- Rust
- Future ecosystems

without requiring those ecosystems to become aware of one another.

## Problem Statement

Most monorepos accumulate metadata across multiple layers:

```text
Root
├── package.json
├── tsconfig.json
├── moon.yml
├── turbo.json
├── nx.json
├── workspace manifests
│
Apps
├── package.json
├── moon.yml
├── tsconfig.json
│
Packages
├── package.json
├── moon.yml
├── tsconfig.json
```

This creates several problems:

### Duplication

Project names exist in:

```text
package.json
moon.yml
documentation
CI configuration
```

### Drift

Configurations gradually diverge.

Example:

```text
package.json
```

says:

```json
{
  "name": "@luna/ui"
}
```

while:

```yaml
project:
  name: ui-library
```

exists elsewhere.

### Discovery Complexity

Tooling must inspect:

```text
package.json
pyproject.toml
go.mod
Cargo.toml
```

to understand the workspace.

### Stack Coupling

JavaScript tooling often becomes the accidental owner of the workspace.

## Design Goals

### Goal 1

Single workspace definition.

Workspace metadata should be defined once.

### Goal 2

Language neutrality.

The workspace should not prioritize:

- TypeScript
- Python
- Go
- Rust

over any other stack.

### Goal 3

Metadata centralization.

Common metadata should live in:

```text
luna.yml
```

instead of being duplicated across projects.

### Goal 4

Moon compatibility.

Moon remains the execution engine.

Luna should integrate with Moon rather than replace it.

### Goal 5

Proto compatibility.

Proto remains the source of truth for toolchains.

## Source of Truth Hierarchy

Luna adopts a three-tier hierarchy.

### Tier 1 — Human Authored

These files are authoritative.

#### Workspace

```text
.prototools
luna.yml
```

#### Purpose

Developers edit these files directly.

### Tier 2 — Generated

Generated by:

```sh
luna sync
```

Examples:

```text
package.json
tsconfig.json
workspace references
generated moon metadata
```

These files are reproducible.

### Tier 3 — Application Owned

Examples:

```text
solid.config.ts
vite.config.ts
hugo.toml
go.mod
Cargo.toml
pyproject.toml
```

These remain manually maintained.

## Workspace Root

The workspace root is determined by:

```text
luna.yml
.prototools
```

Both files must exist.

Example:

```text
repo/
├── luna.yml
├── .prototools
├── apps/
├── packages/
└── crates/
```

## luna.yml

The workspace registry.

### Minimal Example

```yaml
version: 1

workspace:
  name: luna
```

### Full Example

```yaml
version: 1

workspace:
  name: luna
  description: Polyglot workspace runtime
  repository: github.com/luckgrid/luna

toolchains:
  manager: proto
  orchestrator: moon

projects:
  app:
    language: typescript
    framework: solid-start
    layer: application

  api:
    language: python
    framework: fastapi
    layer: application

  web:
    language: go
    framework: hugo
    layer: application

  ui:
    language: typescript
    type: library

  ds:
    language: typescript
    type: library
```

## Project Identity

Projects receive a stable identifier.

Example:

```yaml
projects:
  ui:
```

Produces:

```text
Project ID: ui
```

This ID should never change.

## Project Paths

Projects may be explicitly mapped.

Example:

```yaml
projects:
  app:
    path: apps/app
```

If omitted:

Luna resolves paths automatically.

## Workspace Discovery

Luna discovers projects using:

1. luna.yml
2. Moon metadata
3. Filesystem scanning

in that order.

### Discovery Order

#### Step 1

Read:

```text
luna.yml
```

#### Step 2

Query Moon.

Example:

```sh
moon query projects
```

#### Step 3

Fallback scanning.

Example:

```text
package.json
pyproject.toml
go.mod
Cargo.toml
```

## Moon Integration

Moon remains the execution engine.

Luna never replaces Moon.

### Moon Responsibilities

Moon owns:

```text
Execution
Caching
Task Graph
Dependency Graph
Affected Detection
```

### Luna Responsibilities

Luna owns:

```text
Project Registration
Metadata
Generation
Discovery
```

## Moon Metadata Generation

Future phases may generate:

```text
moon.yml
project metadata
tags
layers
```

from:

```text
luna.yml
```

However:

Moon remains authoritative for execution behavior.

## Proto Integration

### Proto Responsibilities

```text

Tool Versioning
Runtime Discovery
```

### Luna Responsibilities

```text
Toolchain Validation
Workspace Setup
Developer UX
```

## Future Workspace Expansion

Future project types:

```yaml

  docs:
    language: typescript
    framework: astro

  workers:
    language: rust

  infra:
    language: terraform
```

The workspace model should support new ecosystems without architectural changes.

## Acceptance Criteria

The workspace model is complete when:

- luna.yml becomes the workspace registry
- Project registration is centralized
- Workspace discovery is deterministic
- Moon remains execution source of truth
- Proto remains toolchain source of truth
- Additional ecosystems can be added without schema redesign

## Architectural Decision

### Decision

Luna owns workspace metadata.

Moon owns execution.

Proto owns toolchains.

Adapters own ecosystem operations.

### Rationale

This creates a clean separation of responsibilities and avoids duplicating capabilities already provided by Moon, Proto, Bun, uv, Go, and Cargo.

### Consequences

#### Positive

- Reduced metadata duplication
- Easier onboarding
- Cleaner workspace architecture
- Language neutrality

#### Tradeoffs

- Additional Luna layer
- Initial migration effort
- Generated metadata must be validated
